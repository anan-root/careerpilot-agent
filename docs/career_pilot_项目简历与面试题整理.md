### C. 按“背景-目标-过程-结果”讲项目

**背景：**  
中文招聘信息分散在 BOSS 直聘、智联招聘、前程无忧等多个平台，岗位字段格式不统一，用户需要手动组合关键词、筛选岗位、判断简历匹配度、准备面试并整理沟通话术。传统关键词搜索难以处理自然语言求职目标、跨平台岗位对比、个性化推荐和后续沟通边界，因此构建一套覆盖“目标理解-搜索规划-多源采集-简历匹配-推荐解释-受控沟通-面试建议”的求职智能体原型，为个人求职决策提供可解释、可复盘的辅助能力。

**目标：**  
实现面向中文招聘市场的智能岗位检索、简历匹配、推荐排序、受控沟通和面试准备能力，支持用户通过自然语言描述求职目标和沟通边界，自动生成可编辑任务配置，聚合多平台岗位信息，并结合用户简历输出推荐等级、匹配证据、缺失能力、风险点、简历优化动作和面试准备重点。

**过程：**  

- 设计 Agent 编排流程，串联搜索策略、岗位采集、简历画像、推荐排序、报告生成和本地记忆模块，支撑从岗位检索到求职建议的完整闭环。
- 优化自然语言目标解析，将用户输入拆解为城市、关键词、平台、岗位类型、薪资、经验、学历、双休偏好、排除词等 9 类结构化条件。
- 扩展自然语言求职任务解析，把搜索规则、正则筛选、简历匹配阈值、BOSS 打招呼字数和话术边界解析成可编辑配置，用户确认后再执行。
- 构建多平台岗位聚合链路，默认接入 BOSS 直聘、智联招聘、前程无忧，并扩展猎聘、拉勾、牛客、应届生、国聘网等平台入口。
- 统一不同平台的 10+ 岗位字段，并进行去重、筛选、字段完整度统计和平台质量摘要，方便横向比较岗位。
- 设计本地规则粗排 + DeepSeek Top 3 精排的两阶段推荐策略，避免全量调用模型导致响应慢和成本高。
- 将简历画像、岗位匹配、JD 差距分析和面试准备包拆分到 `prompts/` 目录，按版本化 Prompt 管理输入字段和输出结构。
- 引入简历缓存、岗位精排缓存和模型失败兜底机制，DeepSeek 超时、限流或 JSON 解析失败时保留本地评分，保证主流程可用。
- 设计 BOSS 受控沟通层，根据岗位、简历画像、匹配结论和用户提示词生成打招呼/回复草稿，支持字数上限、编辑确认、干跑检查和本地记录。
- 将 Streamlit 页面拆成任务配置、岗位结果、沟通行动、记录记忆 4 个工作区，减少控件堆叠，便于按求职流程推进。

**结果：**  
系统覆盖自然语言岗位搜索、任务配置、多平台岗位聚合、简历画像解析、岗位推荐排序、BOSS 沟通草稿、JD 差距分析、面试准备包生成和本地求职记忆等核心场景。项目将“多平台搜索 -> 岗位筛选 -> 简历匹配 -> 沟通准备 -> 面试准备 -> 结果复盘”6 个环节收束到 1 个本地工作台；默认聚合 3 个主流招聘平台，并支持扩展到 10+ 平台入口；通过本地粗排 + DeepSeek Top 3 精排策略，以 30 个候选岗位为例，模型调用量可由 30 次降至 3 次，理论调用量减少约 90%。

### E. 不到一年经验的 1 分钟介绍

这个项目是一个面向中文招聘市场的求职智能体。用户可以直接输入自然语言目标，比如“上海 AI Agent，20K 以内，社招和校招都可以，不要实习，双休优先”，系统会自动拆解检索条件，去多个招聘平台聚合岗位。上传简历后，系统会根据简历画像重新排序岗位，并输出推荐等级、匹配证据、缺失能力、风险点、简历优化动作和面试准备重点。

技术上，前端用 `Streamlit`，后端用 Python 组织 Agent 流程，主要模块包括搜索策略、岗位聚合、简历画像、推荐排序、报告生成和本地记忆。大模型使用 DeepSeek 的 OpenAI 兼容接口，但不是所有步骤都依赖模型；岗位筛选、字段标准化、本地粗排和异常兜底都由本地规则完成。

我在项目里重点做了两阶段匹配：先用本地规则给全部岗位快速排序，再默认让 DeepSeek 精排 Top 3。这样既能利用模型理解简历和 JD 的能力，也避免每个岗位都调用模型导致速度慢、成本高。对于一个 2025 年毕业、经验不到一年的候选人来说，我会把这个项目作为 AI 应用开发能力的证明，而不是夸成已经大规模上线的商业系统。

#### F.2 你毕业时间不长，为什么能做 Agent 项目？

**回答：**

我理解的 Agent 不是神秘概念，而是把一个复杂任务拆成多个有顺序、有状态、可复盘的步骤。这个项目里用户不是只问一个问题，而是要经历目标解析、搜索计划、多平台采集、简历匹配、推荐解释和面试建议，所以比较适合用 Agent 工作流组织。

我没有一上来做特别复杂的多智能体自治，而是先把流程做清楚：`career_orchestrator.py` 负责编排，搜索策略模块负责计划，采集层负责拿岗位，推荐层负责排序，报告和记忆模块负责沉淀结果。这个实现更偏工程落地，也更适合我目前的经验阶段。

#### F.3 这个项目是不是只是调用大模型接口？

**回答：**

不是。大模型只负责适合语义判断的部分，比如简历画像、岗位精排、JD 差距分析和面试准备包。系统里很多关键步骤是确定性工程流程完成的，比如搜索计划解析、多平台采集、字段标准化、去重、筛选、本地规则粗排、缓存和失败兜底。

如果只是套壳，用户输入会直接丢给模型生成一段回答。但这个项目会先把岗位真实抓回来，统一字段，再基于简历和 JD 做结构化匹配。模型输出也不是随便一段文本，而是推荐分、推荐等级、匹配证据、缺失能力、风险点、简历动作和面试重点这些结构化字段。

#### F.4 你这个项目最大的技术难点是什么？

**回答：**

我觉得主要有三个难点。

第一是自然语言目标不能全部当硬筛选。比如“20K 以内”“双休优先”“去年毕业”这些条件，如果直接硬过滤，很容易把结果过滤没。所以我把条件分成硬条件和软偏好，比如“不要实习”是硬过滤，“双休优先”更多影响排序和风险提示。

第二是模型调用不能全量铺开。岗位可能有几十个，如果每个都调用 DeepSeek，速度和成本都不理想。所以我做了两阶段匹配，本地规则先全量粗排，DeepSeek 默认只精排 Top 3。

第三是 AI 输出要稳定可展示。Prompt 里要求结构化 JSON，代码里还要处理超时、解析失败和字段缺失，失败时保留本地评分，不能让整个页面崩掉。

#### F.5 你简历里写“模型调用减少 90%”，这个数据怎么来的？

**回答：**

这个不是生产环境业务指标，而是基于项目策略计算出来的工程指标。我没有说它提升了真实投递转化率，因为目前项目是个人 MVP，没有大规模用户和埋点。

这里的 90% 指的是模型调用次数。假设一次搜索有 30 个候选岗位，如果每个岗位都让 DeepSeek 精排，就要调用 30 次；现在系统先用本地规则粗排，再默认只让 DeepSeek 精排 Top 3，所以调用次数从 30 次变成 3 次，理论调用量减少约 90%。

#### F.6 如果面试官说这个项目不够生产化，怎么回答？

**回答：**

我会承认它目前不是完整生产系统，而是个人项目和本地演示系统。现阶段重点是把 AI 应用主链路跑通，包括目标理解、多平台采集、简历匹配、推荐解释、报告和记忆。

如果要继续生产化，我会优先补几个方向：异步任务队列和进度展示、用户登录和权限管理、更加稳定的数据源接入、日志监控和错误追踪、测试覆盖、隐私数据管理，以及部署和 CI/CD。这样回答比较真实，也能说明我知道生产系统还需要哪些工程能力。

#### F.7 你在这个项目里最能体现工程能力的点是什么？

**回答：**

我觉得最能体现工程能力的是“把不稳定的大模型能力放进一个稳定流程里”。比如搜索和筛选先走本地规则，模型只做 Top 3 精排；Prompt 拆成独立文件管理；模型输出要求 JSON；同一份简历和同一岗位做缓存；DeepSeek 失败时保留本地评分。

这些设计的目标是让 AI 能增强系统，而不是让系统完全依赖 AI。即使模型接口暂时不可用，用户仍然能看到岗位列表、本地推荐和基础建议。

#### F.8 你为什么选择 Streamlit，而不是 Vue/React？

**回答：**

这个项目的重点是验证 AI 求职 Agent 的主流程，而不是做复杂前端工程。Streamlit 可以快速搭建可交互的本地工作台，方便我把目标输入、简历上传、结果表格、岗位卡片、报告下载和调试信息放在一个页面里。

如果后续要做成正式产品，我会考虑把后端能力拆成 API，再用 Vue 或 React 做更完整的前端。但在 MVP 阶段，Streamlit 更适合快速验证功能闭环。

#### F.9 你处理过哪些异常情况？

**回答：**

主要处理了几类。第一是模型调用异常，比如超时、限流、返回非法 JSON，这种情况下系统会回退本地评分。第二是字段缺失，比如有些平台拿不到双休、地址或经验，系统会标记未知，不会编造。第三是 BOSS 登录态不稳定，所以默认不打开登录浏览器，只有用户显式授权才启动，并且尽量复用同一个会话。

这些处理的目标是保证主流程不断掉，哪怕某个外部平台或模型接口不稳定，页面也不要直接返回空结果。

#### F.10 这个项目和 RAG 有关系吗？

**回答：**

严格说它不是传统知识库 RAG 项目，因为没有单独构建文档向量库和召回链路。但它有 RAG 思想：回答和建议不是凭空生成，而是基于检索到的岗位信息、上传的简历文本和结构化字段生成。

如果后续扩展，我会把历史岗位、面试题、公司信息和用户反馈沉淀成可检索知识库，再加入向量检索和 rerank，让面试准备和岗位推荐更接近完整 RAG 架构。

### G. 初级开发技术追问题库，重点背这部分

> 使用建议：初级开发面试很容易从“项目是做什么的”追到“你具体怎么写的”。回答时不要只讲概念，要主动带出文件、函数、数据结构和异常处理。下面这些问题按常见追问顺序整理。

#### G.1 用户点击“启动 Agent 检索”后，后端完整流程怎么走？

**回答：**

入口在 `app.py`。用户输入目标后，前端调用 `run_agent_search()`。  
`run_agent_search()` 在 `agents/career_orchestrator.py` 里，主要做几件事：先生成 `run_id`，再读取简历画像和本地记忆，然后调用 `build_search_plan()` 生成搜索计划，接着调用 `collect_all_jobs()` 多平台采集岗位。拿到岗位后，如果用户上传了简历，就调用 `rank_jobs_for_resume()` 做本地粗排和 DeepSeek 精排，最后生成报告、保存运行记录，并把结果返回给 Streamlit 展示。

可以简化成：

```text
app.py
-> run_agent_search()
-> build_search_plan()
-> collect_all_jobs()
-> rank_jobs_for_resume()
-> rank_jobs_with_decisions()
-> build_agent_search_report()
-> Streamlit 展示结果
```

#### G.2 你为什么要单独做 `career_orchestrator.py`？

**回答：**

因为这个项目不是单个函数能解决的，它有多个步骤：目标解析、读取记忆、岗位采集、简历匹配、推荐排序、报告生成和异常处理。如果这些逻辑全部写在 `app.py` 里，前端会很乱，也不方便 CLI 复用。

所以我把编排逻辑放到 `career_orchestrator.py`，让 Streamlit 只负责用户交互和展示，后端流程由 Orchestrator 统一调度。这样结构更清楚，也更接近真实项目里的分层设计。

#### G.3 `SearchPlan` 里主要有哪些字段？

**回答：**

`SearchPlan` 本质上是一个字典，里面包括：

- `goal_text`：用户原始输入。
- `keyword`：主关键词，比如 AI Agent。
- `expanded_keywords`：扩展关键词，比如 智能体、大模型应用、RAG、LLM。
- `location`：城市，默认上海。
- `platforms`：平台，比如 boss、zhilian、51job。
- `job_types`：社招、校招或实习。
- `criteria`：薪资、经验、学历、双休等筛选条件。
- `excluded_terms`：排除词，比如外包、实习。
- `safety`：是否允许浏览器登录。
- `notes`：搜索风险说明。

这个结构的价值是把自然语言变成后面采集和筛选都能执行的数据。

#### G.4 自然语言目标是怎么解析的？

**回答：**

目前主要用规则和正则表达式解析，不是直接让大模型解析。比如 `search_strategy_agent.py` 里会识别城市、岗位方向、平台、薪资范围、经验年限、学历、双休和排除词。

例如用户说“上海 AI Agent，20K 以内，不要实习，双休优先”，系统会识别：

- 上海 -> `location`
- AI Agent -> `keyword`
- 20K 以内 -> `salary_preferred_max_k`
- 不要实习 -> 排除实习
- 双休优先 -> `weekend_preferred`

我选择规则解析，是因为这些条件比较明确，规则更稳定、成本更低，也方便解释。

#### G.5 为什么不用大模型做意图识别？

**回答：**

MVP 阶段我优先用了规则，因为求职目标里的很多信息是结构化的，比如城市、薪资、经验、学历、平台名称，用正则和关键词就能稳定提取。  
如果每次搜索计划都调用模型，会增加成本和不确定性，而且模型可能把“20K 以内”“双休优先”理解得不稳定。

后续可以升级成“规则优先 + LLM 补充”的方式：规则能解析的直接解析，复杂表达再交给模型，并要求模型输出 JSON。

#### G.6 “双休优先”和“只看双休”在代码里怎么区分？

**回答：**

在 `search_strategy_agent.py` 里有两个概念：

- `weekend_preferred`：表示偏好，比如“双休优先”。
- `weekend_only`：表示硬条件，比如“只看双休”“不要单休”。

这样做是因为很多招聘平台列表页不会明确写双休。如果用户只是说“双休优先”，我不会直接过滤岗位，而是把它交给推荐排序和风险提示；只有用户明确说“只看双休”，才作为硬筛选。

#### G.7 “20K 以内”为什么不是直接硬过滤？

**回答：**

因为招聘平台的薪资经常是区间，比如 15-25K、18-30K。如果用户说 20K 以内，我直接用上限硬过滤，可能会误删一些仍然可以考虑的岗位。

所以系统把自然语言里的“20K 以内”作为 `salary_preferred_max_k`，优先影响排序和提示。只有用户在明确筛选条件里设置硬范围时，才更接近硬过滤。

#### G.8 岗位数据字段是怎么统一的？

**回答：**

不同平台返回字段不一样，所以采集器会把结果统一成项目内部的标准字段，比如：

- `platform`
- `job_id`
- `title`
- `company`
- `location`
- `salary`
- `experience`
- `degree`
- `welfare`
- `company_address`
- `url`
- `job_type`
- `requirements`

统一字段后，后面的筛选、排序、表格展示和报告生成都可以基于同一套结构处理，不需要每个平台写一套逻辑。

#### G.9 多平台采集是怎么组织的？

**回答：**

核心函数是 `crawlers/aggregator.py` 里的 `collect_all_jobs()`。它先确定平台列表和扩展关键词，然后按平台、按关键词循环调用对应采集器，比如 BOSS、智联、前程无忧、猎聘、牛客等。

采集完成后会做平台内去重、详情页补全、字段增强、筛选、最终去重和统计摘要。摘要里会记录每个平台抓了多少、筛选后剩多少、字段缺失情况，方便前端解释为什么结果少。

#### G.10 你怎么做去重？

**回答：**

去重逻辑在 `crawlers/aggregator.py` 的 `_deduplicate()`。  
如果平台提供了稳定的 `job_id`，就用 `platform + job_id` 做唯一键；如果没有稳定 ID，就用岗位的平台、公司、标题、地点、薪资等字段生成 fingerprint。

这样可以避免同一个平台同一个岗位重复出现，同时也尽量不误删不同平台上的相似岗位。

#### G.11 为什么不直接跨平台去重同名公司同名岗位？

**回答：**

因为不同平台上的同名岗位不一定完全是同一个岗位，薪资、地点、JD、招聘状态可能不同。如果跨平台去重太激进，会误删信息。

所以我当前更保守：优先去掉同平台内的明显重复；跨平台结果保留来源，让用户可以比较不同平台的信息完整度。

#### G.12 岗位筛选怎么处理字段缺失？

**回答：**

在 `job_filters.py` 里，缺失字段通常不会直接当作负面条件。比如一个岗位没有写学历或双休，我不会直接判定它不符合，而是标记未知。

这样做是因为很多平台列表页字段本来就不完整，如果把未知当成不符合，会误删大量岗位。项目更倾向于保留候选，再在结果里提示字段缺失和风险。

#### G.13 薪资字段怎么解析？

**回答：**

薪资解析在 `job_filters.py` 的 `parse_salary_monthly_k()`，会把类似 `15-25K`、`2-3万`、`300元/天` 这类文本尽量解析成月薪 K 的上下限。

解析后会生成 `salary_min_k` 和 `salary_max_k`，方便做筛选和排序。但如果解析不了，就保留原始薪资文本，不强行编造。

#### G.14 为什么有 `enrich_job_fields()`？

**回答：**

`enrich_job_fields()` 的作用是给原始岗位补充统一的派生字段，比如标准化岗位类型、薪资上下限、经验展示、学历展示、双休信息等。

它相当于数据清洗层。采集器只负责尽量拿数据，清洗函数负责把数据变成后续筛选和展示更好用的结构。

#### G.15 简历上传后是怎么解析文本的？

**回答：**

简历解析在 `agents/resume_matcher.py` 的 `extract_resume_text()`。  
它根据文件后缀判断类型，支持 PDF、DOCX、TXT、MD、TEX。TXT/MD/TEX 直接读取文本，PDF 走 PDF 文本提取，DOCX 走 DOCX 文本提取。

提取出的文本会做 normalize，避免多余空白影响后续关键词提取和 hash 缓存。

#### G.16 简历画像怎么生成？

**回答：**

简历画像主要由 `analyze_resume()` 和 `build_resume_profile()` 处理。  
系统会把简历文本填充到 `prompts/resume_profile.md`，让 DeepSeek 按 JSON schema 输出姓名、目标岗位、教育经历、技能、项目、优势和风险。

如果模型调用失败，会回退到本地规则画像，比如根据技术关键词和文本内容提取技能，保证页面不至于因为模型失败而不能用。

#### G.17 本地粗排是怎么打分的？

**回答：**

本地粗排在 `rank_jobs_for_resume()` 里先执行，核心是 `_score_job_against_resume()`。  
它会从简历和岗位文本中提取关键词，然后计算命中情况，比如：

- 简历关键词和岗位关键词重合度。
- 技术技能是否命中。
- 岗位标题是否和目标方向匹配。
- 缺失关键词有哪些。

本地粗排的目标不是做到绝对准确，而是快速把全部候选岗位排个大概顺序，让页面先能返回结果。

#### G.18 DeepSeek 精排怎么接到本地分数里？

**回答：**

在 `rank_jobs_for_resume()` 里，本地分数先排序。然后如果设置了 `ai_top_n`，系统只对前几个岗位调用 DeepSeek。

DeepSeek 返回 `score` 后，会和本地分数融合。当前逻辑是本地分数占 25%，AI 分数占 75%：

```python
final_score = local_score * 0.25 + ai_score * 0.75
```

这样可以保留本地规则的稳定性，同时让 AI 的语义判断对最终排序产生主要影响。

#### G.19 为什么 DeepSeek 默认只精排 Top 3？

**回答：**

这是性能和成本的考虑。岗位候选可能有几十个，如果每个岗位都调用大模型，前端等待时间会很长，API 成本也高。

所以先用本地规则对全部岗位粗排，再默认只让 DeepSeek 精排 Top 3。以 30 个候选岗位为例，全量精排需要 30 次模型调用，现在默认只需要 3 次，理论调用量减少约 90%。

#### G.20 DeepSeek 返回的 JSON 不合法怎么办？

**回答：**

模型调用通过 `llm_client.py` 里的 `chat_json()` 处理，Prompt 里要求输出合法 JSON。  
如果模型返回非法 JSON、超时或报错，`deep_match_resume_to_job()` 会捕获异常，返回一个 `score=None`、`level=AI分析失败` 的结构。

这样前端不会崩，排序也会保留本地评分。普通用户看到的是结果仍然可用，开发者调试区可以看具体错误。

#### G.21 为什么 Prompt 要单独放在 `prompts/` 目录？

**回答：**

因为不同任务的 Prompt 要求不一样。简历画像要输出 JSON，岗位匹配也要输出 JSON，JD 差距分析和面试准备包则输出 Markdown。

如果把这些长 Prompt 全写在 Python 代码里，后续很难维护和调试。所以我把它们拆成文件，并写清楚版本、输入字段和输出结构。业务代码只负责加载 Prompt 和填充变量。

#### G.22 你怎么防止模型胡编？

**回答：**

主要做了三件事。

第一，Prompt 明确要求“只基于简历原文和岗位信息，不要编造”。  
第二，岗位匹配要求输出结构化字段，比如 `matched_evidence` 必须写简历中的真实证据。  
第三，前端展示时把模型结果拆成匹配证据、缺失能力、风险点和简历动作，避免只展示一段看起来很漂亮但无法追溯的文本。

当然，这不能 100% 消除幻觉，所以我会把项目定位为求职辅助工具，而不是自动决策系统。

#### G.23 缓存是怎么做的？

**回答：**

缓存有两类。

第一类是简历缓存。前端会根据上传文件和简历文本生成 hash，同一份简历刷新页面后不重复解析。  
第二类是岗位精排缓存。`_ai_match_cache_key()` 会用简历 hash 加岗位 hash 生成 key，同一份简历和同一个岗位不会重复请求 DeepSeek。

这样可以减少重复调用，也能让页面操作更快。

#### G.24 为什么 cache key 里要包含岗位信息？

**回答：**

因为简历一样，但岗位不一样，匹配结果肯定不同。  
所以 cache key 不能只用简历 hash，还要加入岗位的平台、`job_id`、公司、标题、地点、薪资等信息。

这样才能保证“同一份简历 + 同一个岗位”命中缓存，而不是误用到另一个岗位上。

#### G.25 Streamlit 里怎么保存页面状态？

**回答：**

主要用 `st.session_state`。比如当前岗位列表、搜索摘要、简历画像、分页页码、匹配结果、Agent 结果都会存在 `session_state` 里。

Streamlit 每次交互都会重新执行脚本，如果不用 `session_state`，按钮点击、上传简历、搜索结果和分页状态很容易丢失。

#### G.26 为什么要做表格和卡片两种视图？

**回答：**

表格适合横向比较，比如公司、岗位、薪资、学历、经验。  
卡片适合看单个岗位的详情，比如福利、风险点、匹配证据和简历动作。

所以我做了两种视图：表格用于快速筛选，卡片用于详细决策。卡片还做了分页，避免一次渲染太多内容导致页面很长。

#### G.27 为什么未上传简历时不展示推荐分？

**回答：**

因为没有简历时，系统只能基于岗位本身做基础判断，不是真正的个性化匹配。  
如果这时展示推荐分，用户可能误以为系统已经根据个人经历判断过了。

所以未上传简历时主要展示岗位基础信息；上传简历后，再展示推荐等级、推荐分和匹配解释。

#### G.28 SQLite 在项目里负责什么？

**回答：**

SQLite 主要用来保存岗位数据。`db.py` 里定义了连接、建表、插入岗位、更新岗位分数、查询岗位等函数。

选择 SQLite 是因为这是本地演示项目，不需要一开始就引入 MySQL 或 PostgreSQL。SQLite 文件轻量、部署简单，适合个人项目和 MVP。

#### G.29 数据库怎么避免重复插入？

**回答：**

`jobs` 表里对 `platform` 和 `job_id` 做了唯一约束。插入岗位时，如果发现同平台同 `job_id` 已存在，就更新已有记录里更完整的字段，而不是重复插入一条。

这样可以避免同一个岗位被反复采集后数据库越来越乱。

#### G.30 API Key 是怎么管理的？

**回答：**

API Key 不写死在代码里。项目支持从 `config.local.yaml` 或环境变量读取，比如 `DEEPSEEK_API_KEY`。

`config.local.yaml` 是本地私密配置，不应该提交到 GitHub。这样可以避免密钥泄露，也更符合真实项目里的配置管理方式。

#### G.31 DeepSeek 是怎么调用的？

**回答：**

项目通过 `llm_client.py` 封装模型调用。DeepSeek 使用 OpenAI 兼容接口，所以代码里可以用类似 OpenAI SDK 的方式创建 client，再传入 `base_url`、`api_key`、`model` 等配置。

上层业务模块不直接关心 API 细节，只调用 `chat()` 或 `chat_json()`。这样后续如果要换成其他 OpenAI 兼容模型，改动会比较小。

#### G.32 BOSS 登录为什么要显式授权？

**回答：**

BOSS 这类平台有登录状态和页面确认要求，项目不应该代替用户处理这些人工步骤。  
所以默认不打开 BOSS 登录浏览器，只有用户明确允许时才启动交互式浏览器路径。

这既是使用边界，也是用户体验考虑，避免一运行程序就弹出浏览器或打断用户操作。

#### G.33 你怎么解决 BOSS 多关键词重复开窗？

**回答：**

之前每个关键词可能单独打开一次浏览器，体验不好。后来我把 BOSS 浏览器路径改成批量关键词共用同一个浏览器会话。

也就是说，一轮搜索只创建一次页面，登录成功后在同一个会话里依次搜索多个关键词。这样减少重复开窗，也降低登录态误判带来的问题。

#### G.34 项目里有哪些异常兜底？

**回答：**

主要有几类：

- 模型调用失败：回退到本地评分或本地建议。
- JSON 解析失败：返回结构化失败结果，不让页面崩。
- 平台采集失败：记录该平台失败，其他平台继续执行。
- 字段缺失：标记未知，不编造。
- BOSS 登录失败：保留提示，等待用户按页面要求处理。

核心目标是：外部依赖不稳定时，主流程仍然能返回可用结果。

#### G.35 如果岗位结果很少，你怎么排查？

**回答：**

我会按链路排查：

1. 先看 SearchPlan，确认关键词、城市、平台、岗位类型是不是太窄。
2. 看每个平台抓取数量，判断是平台没抓到，还是抓到了但被过滤。
3. 看筛选条件，比如是否排除了实习、经验上限或薪资条件过严。
4. 看字段完整度，有些平台字段缺失可能影响判断。
5. 最后看去重逻辑是否过于激进。

项目里的搜索摘要会记录平台抓取数、筛选后数量和最终展示数量，就是为了方便这个排查过程。

#### G.36 如果页面卡顿，你会怎么优化？

**回答：**

我会从几个方向优化。

第一，减少首屏等待：先返回本地规则粗排，DeepSeek 精排放到后置。  
第二，减少渲染压力：卡片分页，默认每页 10 条。  
第三，减少重复计算：简历缓存、岗位精排缓存、`st.cache_data`。  
第四，后续可以把采集和模型调用改成异步任务，前端显示每个平台的进度。

#### G.37 这个项目为什么没有一开始用异步？

**回答：**

因为当前项目是个人 MVP，优先目标是把主流程跑通。同步流程更容易调试，也更适合先验证功能闭环。

但从生产化角度看，多平台采集和模型精排都适合做成异步任务。后续可以引入任务队列，比如 Celery、RQ 或 FastAPI 后台任务，前端轮询任务状态。

#### G.38 你怎么验证这个项目功能是正常的？

**回答：**

我主要从几类方式验证：

- 用 Streamlit 页面手动跑完整流程。
- 用 CLI 命令测试 Agent 搜索、最近任务和 Agent 问答。
- 用 `llm-status --test` 检查 DeepSeek 配置和连通性。
- 用固定输入验证 SearchPlan 是否符合预期。
- 看生成的 Markdown 报告和本地运行记录是否完整。

后续如果继续完善，我会补单元测试，重点覆盖搜索计划解析、薪资解析、岗位去重、过滤逻辑和模型失败兜底。

#### G.39 如果让你补测试，你会先测哪些函数？

**回答：**

我会优先测纯函数，因为它们稳定、容易写断言。

比如：

- `build_search_plan()`：测试自然语言能不能解析出正确城市、关键词、薪资、双休和排除词。
- `parse_salary_monthly_k()`：测试不同薪资格式能不能解析。

#### H.1 Python 基础，4 题

##### H.1.1 Python 的 GIL 是干什么的？

**回答：**

GIL 是 CPython 解释器里的全局解释器锁，它保证同一时刻只有一个线程执行 Python 字节码。它主要是为了简化内存管理和对象引用计数的线程安全问题。

它的影响是：多线程对 IO 密集型任务仍然有帮助，比如网络请求、文件读取、模型 API 调用；但对 CPU 密集型任务，比如大量计算，多线程不能真正并行，需要用多进程、C 扩展或异步任务拆分。

结合 CareerPilot 来说，多平台采集、DeepSeek 调用、文件读取更偏 IO 密集，所以后续可以用异步或线程池提升并发；如果要做大量向量计算或模型推理，就更适合独立服务、GPU 或多进程。

##### H.1.2 生成器、迭代器、装饰器分别是什么？

**回答：**

迭代器是可以被 `next()` 逐个取值的对象，实现了 `__iter__()` 和 `__next__()`。  
生成器是一种更简单的迭代器写法，函数里用了 `yield`，不会一次性把所有结果放进内存。  
装饰器本质是一个接收函数并返回新函数的函数，常用于日志、权限、缓存、计时。

简单例子：

```python
def gen_numbers():
    for i in range(3):
        yield i

for x in gen_numbers():
    print(x)
```

装饰器例子：

```python
def log_time(func):
    def wrapper(*args, **kwargs):
        print("start")
        result = func(*args, **kwargs)
        print("end")
        return result
    return wrapper
```

项目里类似 `@st.cache_data` 就是装饰器，用来缓存 Streamlit 数据加载结果。

##### H.1.3 Python 的可变变量和不可变变量怎么理解？

**回答：**

准确说是“可变对象”和“不可变对象”。  
不可变对象包括 `int`、`float`、`str`、`tuple`，修改时会创建新对象。  
可变对象包括 `list`、`dict`、`set`，可以在原对象上修改内容。

项目里大量岗位数据是 `dict`，它是可变对象，所以在函数里修改时要小心副作用。比如如果不想影响原始岗位，可以用 `{**job, "resume_match": match}` 创建一个新字典。

##### H.1.4 魔术方法、静态方法、类方法、实例方法分别是什么？

**回答：**

魔术方法是 Python 里双下划线开头和结尾的方法，比如 `__init__`、`__str__`、`__len__`、`__iter__`，用于让对象支持初始化、打印、长度、迭代等内置行为。

实例方法第一个参数是 `self`，可以访问实例属性。  
类方法用 `@classmethod`，第一个参数是 `cls`，适合操作类级别状态或做备用构造函数。  
静态方法用 `@staticmethod`，不依赖 `self` 或 `cls`，更像放在类命名空间里的普通工具函数。

CareerPilot 主要是函数式模块组织，没有大量类；如果后续把 SearchPlan 做成类，可以用 `__init__` 初始化，用实例方法做校验，用静态方法做字段清洗。

#### H.2 知识库 / RAG / 数据库，15 题

##### H.2.1 RAG 的发展历史简述

**回答：**

RAG 可以理解为从“模型只靠参数记忆回答”发展到“先检索外部知识，再让模型基于证据回答”。早期更多是 BM25、倒排索引这类关键词检索；后来有了向量 embedding，可以按语义召回；再后来出现混合检索，也就是 BM25 + Dense Vector + Rerank；现在还会结合 Agent、GraphRAG、多模态检索和工具调用。

结合 CareerPilot 来说，它不是标准知识库 RAG，但有 RAG 思想：回答和建议不是凭空生成，而是基于检索到的岗位信息、上传简历和结构化字段生成。

##### H.2.2 RAG 的分块策略你用的是什么，为什么？

**回答：**

CareerPilot 当前没有做传统知识库分块，因为它处理的是岗位结构化数据和简历文本，不是长文档知识库。

如果扩展成面试知识库或岗位知识库，我会采用“按结构优先 + 适当重叠”的分块策略。比如简历按项目经历、技能、教育经历分块；JD 按岗位职责、任职要求、加分项分块；长文档按标题和段落切分，每块控制在 500 到 800 token，并保留 50 到 100 token overlap。

原因是语义边界清楚，召回时不容易把一个完整要求切断，同时 overlap 能减少上下文断裂。

##### H.2.3 为什么要做 RAG？了解 Elasticsearch 吗？

**回答：**

做 RAG 是为了解决大模型知识过时、容易幻觉、无法追溯来源的问题。检索先把相关资料找出来，生成时要求模型基于检索内容回答，可以提升可靠性。

Elasticsearch 我了解它主要基于倒排索引，适合关键词检索、过滤、排序、聚合和日志检索。传统 RAG 里可以用它做 BM25 召回，也可以结合向量检索做混合检索。

CareerPilot 目前没有接 Elasticsearch，而是本地 SQLite + 多平台采集 + 规则筛选。如果后续岗位量变大，可以把岗位标题、JD、公司信息写入 ES，用 BM25 召回，再结合向量检索和 rerank。

##### H.2.4 RAG 的 embedding 模型用哪个，为什么？

**回答：**

CareerPilot 当前没有落地 embedding 模型，因为还没有做向量知识库。

如果做中文求职知识库，我会优先考虑 `bge-m3` 或中文效果较好的 bge 系列模型。原因是它对中英文混合文本支持比较好，适合岗位 JD、简历、面试题这类语义匹配场景。如果只是本地轻量 demo，可以用更小的 embedding 模型降低资源消耗。

##### H.2.5 为什么选择小模型作为 RAG 调用模型？

**回答：**

RAG 场景里，如果检索上下文已经比较准确，生成模型不一定非要特别大。小模型的优势是成本低、延迟低、部署更容易。

但我会区分任务：分类、改写、摘要可以用小模型；最终答案生成、复杂推理和结构化分析可以用能力更强的模型。CareerPilot 里也是类似思路：本地规则先处理确定性部分，DeepSeek 只处理简历精排、差距分析和面试准备这类语义任务。

##### H.2.6 你的 NL2SQL 是怎么实现的？

**回答：**

CareerPilot 当前没有完整 NL2SQL。它的数据库查询主要是固定条件查询，比如按平台、状态、分数查询岗位。

如果要扩展 NL2SQL，我会这样做：先把数据库 schema、字段注释、可用表和示例 SQL 提供给模型；要求模型只生成 `SELECT`，禁止 `UPDATE/DELETE`；生成后先做 SQL 安全校验和语法检查；执行失败时把错误信息回传给模型重试；最后再把 SQL 结果交给模型总结。

比如用户问“上海 20K 以内 AI Agent 岗位有哪些”，可以先转 SQL 查 SQLite，再把结果给生成层回答。

##### H.2.7 有没有做到 SQL 和向量数据库双联动？

**回答：**

CareerPilot 当前没有做到 SQL + 向量数据库双联动。现在主要是结构化筛选、关键词和本地规则匹配。

如果扩展，我会做两种联动方式：  
第一种是 SQL 先过滤结构化条件，比如城市、薪资、平台、岗位类型，再对过滤后的 JD 做向量相似度召回。  
第二种是 SQL 和向量检索并行召回，再对结果去重、合并和 rerank。

这样既能利用 SQL 的精确过滤，也能利用向量检索的语义召回。

##### H.2.8 RAG 的评测怎么做，指标有哪些？

**回答：**

RAG 评测一般分检索评测和生成评测。

检索侧看 `Recall@K`、`Precision@K`、`MRR`、`nDCG`、命中率、上下文相关性。  
生成侧看忠实度、相关性、答案完整性、引用准确率、幻觉率、人工评分。  
工程侧还要看延迟、QPS、成本、缓存命中率。

CareerPilot 目前没有完整 RAG 评测，但有类似的质量摘要，比如平台抓取量、筛选后数量、字段完整度、DeepSeek 精排成功数。后续如果做知识库，会补标准 RAG 评测集。

##### H.2.9 PostgreSQL 和 MySQL 掌握到什么程度？

**回答：**

我了解它们都是关系型数据库，支持表、主键、索引、事务和 SQL 查询。MySQL 更常见于业务系统，生态成熟；PostgreSQL 类型系统、复杂查询、JSON、扩展能力更强，也常用于需要更强 SQL 能力的场景。

CareerPilot 当前用 SQLite，因为是本地 MVP。后续如果多人使用或部署成服务，我会考虑迁移到 PostgreSQL 或 MySQL，把岗位表、用户表、投递记录、反馈记录拆出来。

##### H.2.10 数据库有哪些类型？向量数据库怎么选？

**回答：**

数据库可以分为关系型和非关系型。关系型包括 MySQL、PostgreSQL、SQLite；非关系型包括 MongoDB、Redis、Elasticsearch、图数据库、向量数据库等。

向量数据库常见有 Milvus、FAISS、ChromaDB。  
Milvus 适合数据量较大、服务化部署和高并发检索。  
FAISS 更适合本地实验、单机向量检索和数据量不大的场景。  
ChromaDB 上手简单，适合原型和 LangChain demo。

索引方面，Flat 精确但慢；IVF 先聚类再检索，速度更快但可能牺牲召回；HNSW 常用于高效近似最近邻。距离度量常见有 L2、余弦相似度和内积。

##### H.2.11 为了解决大模型幻觉，你用了哪些方法？

**回答：**

CareerPilot 里主要做了这些：

- Prompt 要求只基于简历原文和岗位信息回答。
- 岗位匹配要求输出结构化 JSON。
- `matched_evidence` 必须来自简历或岗位信息。
- 没有证据就输出缺失能力或风险点，不让模型编造。
- 模型失败时回退本地规则，不让错误扩散。
- 普通界面展示匹配证据、缺失能力和风险点，而不是只展示一段生成文本。

核心思路是：让模型基于可追溯输入生成，并且把输出结构化。

##### H.2.12 图片召回有没有经验？

**回答：**

CareerPilot 没有做图片召回。  
我了解常见方案是：如果是图片里的文字，先 OCR 提取文本，再走文本检索；如果是图片语义召回，可以用 CLIP 或多模态 embedding，把图片和文本映射到同一个向量空间，再做相似度搜索。

比如招投标系统里扫描件、营业执照、产品图，可以先 OCR + 图片 embedding 双路召回，再 rerank。

##### H.2.13 LangChain 的组件了解多少？

我了解 LangChain 常见组件包括：Model、PromptTemplate、OutputParser、Retriever、VectorStore、Tool、Agent、Memory、Chain/Runnable、Callback。

##### H.2.14 压测和 QPS 怎么理解？

**回答：**

QPS 是每秒请求数，压测主要看系统在并发下的吞吐、平均延迟、P95/P99 延迟、错误率、CPU/内存、外部 API 调用耗时。

CareerPilot 目前没有正式压测。它的主要瓶颈会在招聘平台请求、详情页抓取和 DeepSeek 调用。如果要压测，我会先把采集和模型调用拆成接口，再用 Locust 或 wrk 测接口，并加缓存、限流和异步队列。

#### H.3 Agent，15 题

##### H.3.1 Agent 这块用的什么框架？

**回答：**

CareerPilot 没有使用 LangGraph 或 AutoGen，而是自己实现了轻量 Agent 编排。核心是 `career_orchestrator.py`，它按固定流程串联搜索计划、岗位采集、简历画像、推荐排序、报告生成和本地记忆。

这样做是因为项目规模不大，固定流程更容易调试，也更适合我作为初级开发先把主链路做清楚。

##### H.3.2 谈谈你对 Agent 的理解

**回答：**

我理解的 Agent 是一个能围绕目标进行计划、调用工具、读取记忆、观察结果并继续执行的系统。它不只是一次模型问答，而是有状态、有步骤、有工具调用的任务流程。

CareerPilot 里用户目标不是一次问答能完成的，所以我把它拆成：理解目标、生成计划、检索岗位、匹配简历、生成建议、保存记忆。

##### H.3.3 LangGraph 和 AutoGen 了解吗？

**回答：**

了解基本思路。LangGraph 更像状态图，把任务拆成节点和边，用状态在节点之间流转，适合可控的复杂 Agent 流程。AutoGen 更偏多 Agent 对话协作，不同角色的 Agent 互相讨论和调用工具。

CareerPilot 当前没用它们，但如果升级，我会优先考虑 LangGraph，因为求职流程本身比较像状态机。

##### H.3.4 如果用 LangGraph，边和节点怎么设置？

**回答：**

我会把节点设计成：

```text
ParseGoal -> BuildSearchPlan -> CrawlJobs -> FilterJobs -> BuildResumeProfile -> RankJobs -> GenerateReport -> AnswerQuestion
```

边可以根据状态条件跳转。比如没有上传简历，就跳过 `BuildResumeProfile` 和 DeepSeek 精排；平台采集失败，就进入 fallback；用户追问时进入 `AnswerQuestion`。

##### H.3.5 怎么解决 Agent 陷入死循环？

**回答：**

常见方法有：

- 设置最大步数和最大工具调用次数。
- 明确终止条件，比如已经生成报告就停止。
- 记录已经执行过的工具和参数，避免重复调用。
- 工具返回结构化状态，失败次数超过阈值就 fallback。
- 对高风险操作加人工确认。

CareerPilot 当前是固定流程编排，不是自由循环 Agent，所以天然减少了死循环风险。

##### H.3.6 多 Agent 和单 Agent 相比，缺点在哪里？

**回答：**

多 Agent 的缺点是链路更复杂、延迟更高、成本更高、调试更难，也容易出现多个 Agent 观点不一致或互相等待的问题。

所以不是所有项目都需要多 Agent。CareerPilot 当前用单 Orchestrator + 多模块更合适，流程清楚、可控、成本低。

##### H.3.7 懂不懂强化学习驱动 Agent？

**回答：**

我了解基本概念。强化学习驱动 Agent 是通过奖励信号优化 Agent 的策略，比如工具选择、步骤规划、任务完成率。常见思路包括 RLHF、RLAIF、基于轨迹的偏好优化、用成功/失败任务给 Agent 学习。

CareerPilot 没有做强化学习。后续如果要做，可以把用户反馈、投递结果、面试结果作为弱奖励信号，用来优化推荐排序或策略选择。

##### H.3.8 Function Calling 和 MCP 的区别？

**回答：**

Function Calling 是模型在一次对话里按照 schema 生成函数调用参数，由应用执行函数并把结果返回给模型。它更像“模型调用应用内函数”的能力。

MCP 是一种更通用的工具和上下文协议，用来让客户端连接不同的工具、资源和服务。它不只是函数 schema，还包括资源、工具、提示词等能力的标准化暴露。

简单说：Function Calling 偏模型接口能力；MCP 偏工具生态和上下文接入协议。

##### H.3.9 有没有用过 Skills？说说原理

**回答：**

了解。Skills 可以理解成给 Agent 的可复用能力包，里面通常包含说明文档、执行步骤、脚本、模板或约束。Agent 在遇到特定任务时加载对应 Skill，就能按这个领域的最佳实践执行。

CareerPilot 里也有 `skill/SKILL.md`，可以把项目能力包装成可复用说明，让 Agent 知道这个项目怎么运行、怎么搜索岗位、怎么生成建议。

##### H.3.10 Superpower 的组件有哪些？

**回答：**

这个不属于 CareerPilot 项目本身。如果面试官问，我会谨慎回答：我了解这类 Agent 工具通常会包含模型调用、工具执行、文件系统、浏览器/搜索、记忆、Skills、MCP 连接、任务调度等组件。

我不会把 Superpower 的能力说成 CareerPilot 已经使用。CareerPilot 自己实现的是本地记忆、Prompt 管理、模型调用和固定流程编排。

##### H.3.11 Claude Code 常用快捷键或命令了解吗？

**回答：**

这不是 CareerPilot 的项目重点。我会回答我主要使用代码助手完成读文件、改代码、运行命令、看 diff、执行测试这类流程。具体到不同工具，常见操作包括清空上下文、压缩上下文、切换模型、查看帮助、停止当前生成等。

如果面试官追具体快捷键，我会说我更关注工程流程本身，不会把某个工具快捷键包装成项目能力。

##### H.3.12 OpenClaw / Hermes Agent 的记忆和心跳机制了解吗？

**回答：**

了解基本方向，但 CareerPilot 没有使用 OpenClaw 或 Hermes Agent。  
这类 Agent 工具通常强调持久记忆、技能系统和定时唤醒。记忆机制用于跨会话保存用户偏好、任务状态和历史经验；心跳机制可以让 Agent 按时间间隔主动醒来，检查任务列表或记忆，看是否需要继续执行。

结合 CareerPilot，如果后续要做“每天自动检查新岗位并提醒我”，就可以借鉴心跳机制：定时读取求职目标和历史反馈，自动搜索新岗位，然后生成日报。

##### H.3.13 谈谈你对记忆机制的认识

**回答：**

我理解 Agent 记忆可以分短期记忆和长期记忆。短期记忆是当前对话上下文；长期记忆是跨会话保存的用户偏好、历史反馈、任务记录和总结。

CareerPilot 里有本地记忆，保存简历画像、搜索历史、岗位反馈、投递状态和 Agent 运行记录。它的作用是让下一次搜索能参考之前的结果，而不是每次从零开始。

##### H.3.14 多轮对话是怎么实现的？

**回答：**

多轮对话的关键是保存上下文。CareerPilot 里用户可以基于最近一次 Agent 搜索结果继续提问，比如“为什么结果少”“优先投哪个”。  
`conversation_agent.py` 会读取最近一次搜索的计划、岗位、摘要和推荐结果，再根据问题类型生成回答。

它不是完全开放式聊天，而是围绕当前搜索上下文做本地问答，这样更可控，也更不容易幻觉。

##### H.3.15 Agent 怎么解决幻觉问题？

**回答：**

主要靠约束和可追溯输入：

- 明确工具返回结果，模型不能凭空编造。
- 生成回答时附带依据，比如岗位字段、简历证据。
- 没有数据时回答“不确定”或“字段缺失”。
- 限制工具调用范围，避免乱查乱写。
- 对模型输出做结构化解析和兜底。

CareerPilot 里尤其强调：字段缺失不编造，DeepSeek 失败保留本地评分。

#### H.4 微调，5 题

##### H.4.1 微调的数据集怎么来？

**回答：**

CareerPilot 没有做模型微调。  
如果要微调，数据集可以来自真实任务样本，比如简历原文、岗位 JD、人工标注的匹配等级、缺失能力、简历建议和面试题。也可以用历史高质量问答、人工审核后的模型输出构造 SFT 数据。

关键是数据要脱敏，不能泄露个人简历、手机号、公司内部信息。

##### H.4.2 微调参数怎么设置？

**回答：**

如果是 LoRA 微调，常见参数包括学习率、batch size、epoch、LoRA rank、alpha、dropout、最大长度、warmup、保存间隔。  
初始可以用较小学习率，比如 `1e-4` 或 `2e-4`，epoch 不宜太大，避免过拟合。最终参数要看数据量、模型大小和验证集效果。

这个项目没做微调，所以我不会说自己调过生产参数。

##### H.4.3 LoRA 和 QLoRA 怎么理解？

**回答：**

LoRA 的核心思想是冻结大模型原始参数，只在部分线性层旁边加低秩矩阵，让训练只更新这些小矩阵。这样显存和训练成本更低。

LoRA 改的是新增的低秩适配器参数，不直接改原始大模型参数。  
QLoRA 是在量化基础上做 LoRA，通常把基座模型用 4bit 量化加载，再训练 LoRA 适配器，进一步降低显存占用。

##### H.4.4 微调难吗？怎么部署，用什么卡？

**回答：**

微调难点不只是训练命令，而是数据质量、任务定义、评测和部署。数据差的话，参数调得再好也没用。

我这个项目没有实际做微调部署。如果做小规模 LoRA，可以用单张 24GB 显存的卡尝试 7B 级模型；更大模型需要更多显存或量化、梯度检查点、Deepspeed 等优化。生产部署还要考虑推理框架、并发、显存占用和模型版本管理。

##### H.4.5 微调时 loss function 怎么计算？

**回答：**

大语言模型 SFT 常用的是 next token prediction，也就是给定前面的 token，预测下一个 token。Loss 通常是交叉熵损失，对模型预测分布和真实下一个 token 做比较。

简单说，模型每生成一个 token 都会有一个预测概率，真实 token 概率越高，loss 越低。训练就是通过反向传播让正确 token 的概率变高。

#### H.5 深度学习 / 机器学习，5 题

##### H.5.1 SVM 的核函数有哪些？

**回答：**

常见核函数有线性核、多项式核、RBF 高斯核、Sigmoid 核。  
线性核适合线性可分或高维稀疏特征；RBF 更常用，能处理非线性边界；多项式核可以拟合多项式关系，但参数敏感。

##### H.5.2 复述 Transformer，Softmax、Top-K、Top-P、Temperature、残差、层归一化怎么理解？

**回答：**

Transformer 核心是自注意力机制。输入 token 先变成 embedding，再加位置编码，然后进入多层 Transformer Block。每层通常包括多头注意力、残差连接、层归一化和前馈网络。

Softmax 把 logits 转成概率分布。  
Top-K 是只从概率最高的 K 个 token 里采样。  
Top-P 是从累计概率达到 P 的候选集合里采样。  
Temperature 控制随机性，越高越发散，越低越保守。  
残差连接缓解深层网络训练困难，让梯度更容易传递。  
层归一化稳定每层输入分布。  
旋转位置编码 RoPE 是一种把位置信息编码进注意力计算的方法，很多现代大模型会用。

##### H.5.3 前向传播、反向传播、梯度消失和梯度爆炸怎么理解？

**回答：**

前向传播是输入经过模型得到预测结果和 loss。  
反向传播是根据 loss 对参数求梯度，再用优化器更新参数。

梯度消失是反向传播时梯度越来越小，前面层几乎学不动。梯度爆炸是梯度过大，训练不稳定。  
解决方法包括合适初始化、残差连接、归一化、梯度裁剪、合适激活函数和学习率调整。

##### H.5.4 BERT 和 GPT 怎么理解？

**回答：**

BERT 是 Encoder-only 架构，擅长理解类任务，比如分类、匹配、抽取。它通过 Masked Language Model 训练，可以看双向上下文。  
GPT 是 Decoder-only 架构，擅长生成类任务，通过自回归方式预测下一个 token。

简单说，BERT 更偏理解，GPT 更偏生成。现在很多大模型都是 GPT 类 Decoder-only 架构。

##### H.5.5 实体关系抽取怎么做？

**回答：**

实体关系抽取一般分两步：先识别实体，再判断实体之间的关系。传统方法可以用规则、CRF、分类模型；深度学习方法可以用 BERT 做 NER，再用分类器判断关系；大模型方法可以用 Prompt 让模型按 JSON 输出实体和关系。

如果结合 CareerPilot，可以抽取“公司-岗位”“岗位-技能”“岗位-学历”“岗位-薪资”这些关系，后续构建求职知识图谱。

#### H.6 后端，7 题

##### H.6.1 异步函数、高并发、async、await、线程池、进程池怎么理解？

**回答：**

`async` 定义协程函数，`await` 等待一个异步操作，`asyncio.run()` 用来启动事件循环。异步适合 IO 密集型任务，比如网络请求、数据库请求、模型 API 调用。

线程池适合把阻塞 IO 放到后台线程，避免卡住主线程；进程池适合 CPU 密集型任务，因为可以绕开 GIL 做多核并行。

CareerPilot 当前主要是同步流程，后续多平台采集和 DeepSeek 精排可以改成异步或任务队列，提高响应速度。

##### H.6.2 线程和进程的区别？

**回答：**

进程是资源分配单位，有独立内存空间；线程是进程里的执行单位，共享同一个进程的内存。  
进程隔离性好，但创建和通信成本更高；线程更轻量，但共享内存会带来线程安全问题。

Python 里 CPU 密集型任务常用多进程，IO 密集型任务可以用多线程或异步。

##### H.6.3 127.0.0.1、localhost、Docker 端口映射、内网穿透、路由、域名怎么理解？

**回答：**

`127.0.0.1` 是本机回环地址，`localhost` 通常解析到本机。  
Docker 端口映射是把容器内端口映射到宿主机端口，比如 `-p 8501:8501`。  
内网穿透是把本地服务临时暴露到公网，比如用于测试回调。  
路由是请求路径到处理函数的映射。  
域名是更好记的地址，通过 DNS 解析到 IP。

CareerPilot 本地用 Streamlit 启动，默认访问本机端口；如果部署到服务器，就需要考虑端口、防火墙、域名和反向代理。

##### H.6.4 会用 Linux 系统吗？

**回答：**

会基础使用。常用命令包括 `ls`、`cd`、`cat`、`grep/rg`、`ps`、`kill`、`top`、`df`、`du`、`chmod`、`ssh`、`scp`、`systemctl`、`tail -f`。  
部署 Python 项目时会创建虚拟环境、安装依赖、设置环境变量、查看日志和排查端口占用。

##### H.6.5 Redis 存储短期记忆怎么做？

**回答：**

Redis 适合存短期状态，比如会话上下文、临时校验状态、任务进度、限流计数和缓存。  
如果把 CareerPilot 做成 Web 服务，可以用 Redis 保存用户最近一次搜索结果、Agent 临时状态、模型调用缓存，并设置 TTL 自动过期。

长期数据，比如岗位、投递记录和用户画像，还是更适合放数据库。

##### H.6.6 分布式锁对多人同时操作一个文件有什么作用？

**回答：**

分布式锁用于保证同一时刻只有一个实例执行某个关键操作。  
如果多人或多个服务同时写同一个文件，可能出现覆盖、内容错乱或数据丢失。用 Redis 分布式锁可以在写文件前先抢锁，写完再释放锁，避免并发写冲突。

CareerPilot 当前是本地单人使用，没有分布式锁。如果做多人版本，写报告、更新记忆或导出文件时就要考虑并发控制。

##### H.6.7 FastAPI 掌握到什么程度？

**回答：**

我了解 FastAPI 的基本使用，包括定义路由、请求参数、Pydantic 数据模型、依赖注入、异步接口、异常处理和自动生成 OpenAPI 文档。

CareerPilot 当前用 Streamlit 做前端，没有拆 FastAPI 后端。如果生产化，我会把 `run_agent_search()`、简历上传、岗位查询、反馈保存、报告下载拆成 FastAPI 接口，前端再用 Vue 或 React 调用。

## 0. 最新项目口径

现在这个项目建议按“AI 求职 Agent”来讲，而不是按“招聘网站爬虫”来讲。

核心闭环是：

用户输入求职目标或求职任务 -> Agent 生成搜索计划或任务配置 -> 多平台采集岗位 -> 本地快速筛选和排序 -> 上传简历后自动解析画像 -> DeepSeek 对本地 Top 3 岗位精排 -> 输出推荐等级、推荐分、匹配证据、缺失能力、风险点、简历动作和面试重点 -> 生成 BOSS 沟通草稿、JD 差距分析和面试准备包 -> 保存报告和求职记忆。

面试时最值得强调的四个点：

1. **两阶段匹配**  
   先本地规则快速给全部岗位排序，再用 DeepSeek 精排 Top 3，兼顾速度、成本和准确性。

2. **结构化 AI 输出**  
   DeepSeek 不只是生成一段建议，而是输出 `ai_match` 结构：推荐分、推荐等级、匹配证据、缺失能力、风险点、简历动作和面试重点。

3. **Prompt 工程化**  
   把简历画像、岗位匹配、JD 差距分析、面试准备包拆成 `prompts/` 目录下的版本化 Prompt 文件，不把长提示词散落在业务代码里。

4. **产品化收束**  
   普通界面不展示 JSON，所有模型结果都转成中文可读卡片；原始 JSON 只放在默认关闭的开发者调试区。

5. **受控沟通边界**  
   BOSS 沟通不是自动投递，而是“生成草稿 -> 用户编辑 -> 干跑检查 -> 用户确认 -> 单岗位发送”的受控流程。

### 0.1 提效、降本、增速指标口径

这些指标适合写进简历或面试中，但要按“本地演示 / MVP 验证”口径表达，不包装成生产环境真实业务数据：

| 指标方向 | 可量化口径 | 面试解释 |
|---|---|---|
| 流程提效 | 将“多平台搜索 -> 条件筛选 -> 岗位对比 -> 简历匹配 -> 面试准备”5 个动作收束到 1 个工作台 | 原来需要在多个招聘网站和文档之间来回切换，现在用一个 Agent 流程串起来 |
| 检索提效 | 自然语言目标解析为 9 类结构化条件 | 城市、关键词、平台、岗位类型、薪资、经验、学历、双休偏好、排除词，不需要用户手动组合所有筛选项 |
| 任务复用 | 自然语言任务保存到本地 JSON | 用户可以保存“搜索 + 筛选 + 匹配 + 沟通边界”，下次加载后继续使用 |
| 覆盖提升 | 默认聚合 3 个主平台，可扩展到 10+ 平台入口 | 默认 BOSS、智联、前程无忧；平台注册表里还保留猎聘、拉勾、牛客、应届生、国聘等入口 |
| 字段统一 | 不同平台岗位统一为 10+ 标准字段 | 公司、岗位、薪资、经验、学历、福利、地址、工作制、来源链接、岗位类型等，便于横向比较 |
| 模型降本 | DeepSeek 精排请求从 N 次降到默认 3 次 | 若一轮搜索有 30 个候选，全量精排要 30 次模型调用，默认 Top 3 精排只需要 3 次，理论调用量下降 90% |
| 首屏增速 | 本地规则先全量评分，DeepSeek 只做后置增强 | 页面不用等所有模型调用结束，先展示本地排序结果，再补充 AI 精排证据 |
| 重复调用减少 | 简历画像缓存 + 岗位精排缓存 | 同一份简历用文本 hash 缓存；同一简历 + 同一岗位命中缓存后不重复请求 DeepSeek |
| 浏览提效 | 卡片默认 10 条/页，支持表格/卡片双视图 | 避免一次渲染几十条卡片导致页面过长，表格用于快速比较，卡片用于看详情和行动建议 |
| 界面降噪 | 拆成 4 个 Streamlit 工作区 | 任务配置、岗位结果、沟通行动、记录记忆分开展示，避免控件全部堆在首屏 |
| 沟通可控 | 单岗位草稿确认机制 | 先生成打招呼/回复草稿，用户编辑确认后才执行，不做批量和自动代聊 |
| 稳定性兜底 | 模型失败时保留本地评分，不返回空结果 | DeepSeek 超时、限流、JSON 解析失败时，主流程继续可用，只标记 AI 精排失败 |

最适合写在简历里的成果句：

- 将求职流程从多平台手工搜索和人工对比，收束为 1 个 Streamlit 工作台，覆盖目标解析、岗位检索、简历匹配、推荐解释和面试建议 5 个环节。
- 设计“本地规则全量粗排 + DeepSeek Top 3 精排”策略；以 30 个候选岗位为例，模型调用从 30 次降到 3 次，理论调用量减少约 90%。

## 4. 项目架构怎么讲

### 4.1 按层讲

可以把项目分成七层：

1. **前端交互层**  
   使用 `Streamlit`，负责目标输入、简历上传、筛选项、岗位结果、卡片分页、报告下载和本地问答。

2. **Agent 编排层**  
   `career_orchestrator.py` 负责把简历画像、求职记忆、搜索计划、岗位检索、推荐排序和报告生成串起来。

3. **搜索计划层**  
   `search_strategy_agent.py` 负责把自然语言目标解析成城市、关键词、岗位类型、平台、薪资、经验、学历、双休和排除词。

4. **岗位采集层**  
   `crawlers/aggregator.py` 统一调度 BOSS、智联、前程无忧等平台采集器，处理关键词扩展、平台统计、去重和字段完整度。

5. **推荐匹配层**  
   `resume_matcher.py` 和 `ranking_agent.py` 负责简历解析、岗位匹配、推荐等级、推荐分、风险点和简历动作。匹配采用本地快速评分 + DeepSeek Top 3 精排。

6. **Prompt 与模型调用层**  
   `prompts/` 和 `prompt_loader.py` 负责管理版本化 Prompt，`llm_client.py` 负责读取本地配置或环境变量并调用 DeepSeek。

7. **存储与报告层**  
   `db.py`、`memory/store.py` 和 `report_agent.py` 负责岗位库、本地记忆、运行记录、搜索历史、反馈记录和 Markdown 报告。

### 4.2 一句话架构

Streamlit 负责交互，Career Orchestrator 负责任务编排，Search Strategy 负责计划生成，Crawler Aggregator 负责多平台岗位聚合，Ranking/Matcher 负责两阶段推荐解释，Prompt Loader 和 LLM Client 负责 DeepSeek 能力接入，SQLite 和 JSONL 负责本地存储。

### 4.3 请求链路

用户启动 Agent 检索后的链路：

1. 用户在 Streamlit 前端输入求职目标，可选上传简历。
2. 前端调用 `run_agent_search`。
3. Orchestrator 读取简历画像和本地求职记忆。
4. Search Strategy 解析目标，生成结构化 SearchPlan。
5. Aggregator 根据平台和关键词采集岗位。
6. 系统统一字段、去重、筛选，并统计平台结果和字段完整度。
7. 如果有简历，系统自动解析并缓存简历画像。
8. Resume Matcher 先用本地规则快速匹配全部岗位。
9. DeepSeek 默认精排本地 Top 3 岗位，失败时保留本地评分。
10. Ranking Agent 生成推荐等级、推荐解释、风险点和行动建议。
11. Report Agent 生成 Markdown 报告。
12. Memory Store 保存搜索历史、岗位反馈、投递记录和运行记录。
13. 前端展示表格、卡片、分页、推荐解释和报告下载入口。

## 5. 高频面试题与回答

### 5.1 这个项目是做什么的？

**回答：**

这个项目是一个中文求职智能体。用户输入求职目标后，系统会自动生成搜索计划，并从 BOSS、智联、前程无忧等平台聚合岗位。用户上传简历后，系统会进一步做岗位匹配和推荐排序，输出推荐等级、匹配理由、风险点、简历优化建议和面试准备重点。

它的核心不是单纯爬岗位，而是把岗位搜索、简历匹配、推荐解释和行动建议串成一个闭环。

**可以补一句：**

我在项目里重点做了 Agent 编排、多平台字段统一、简历画像匹配和 BOSS 登录浏览器的体验优化。

---

### 5.2 它和普通招聘爬虫有什么区别？

**回答：**

普通招聘爬虫主要解决“把岗位抓下来”的问题，但这个项目解决的是“岗位是否适合我，以及下一步该怎么行动”的问题。

CareerPilot Agent 会先理解用户的求职目标，生成搜索计划；然后聚合岗位、去重、筛选；上传简历后，还会根据简历画像做推荐排序，并解释为什么推荐、哪里有风险、简历该补什么内容、面试该准备什么。

所以它不是简单的数据采集，而是一个求职决策助手。

---

### 5.2.1 它和普通大模型套壳有什么区别？

**回答：**

普通大模型套壳往往是把用户输入直接丢给模型，让模型生成一段回答。这个项目不是这样，它先用确定性流程完成搜索计划、平台采集、字段标准化、去重、筛选和本地评分，然后只在适合大模型发挥的地方调用 DeepSeek，比如简历画像、岗位精排、JD 差距分析和面试准备包。

我还把 Prompt 文件化，并要求模型输出结构化字段。前端不会直接展示 JSON，而是把结果转成推荐分、推荐等级、匹配证据、缺失能力、风险点和行动建议。这样系统既有工程流程的稳定性，也能利用大模型的语义判断能力。

---

### 5.3 为什么要做成 Agent？

**回答：**

因为这个任务不是单步操作，而是一条连续链路。用户目标需要被理解，筛选条件要区分硬条件和偏好，岗位需要跨平台采集和统一，简历需要解析，推荐结果还要解释和生成建议。

Agent 的价值在于把这些步骤组织成一个流程：先计划，再采集，再匹配，再解释，再保存记忆。这样用户下次继续搜索时，也可以基于历史反馈迭代。

---

### 5.4 自然语言目标怎么变成搜索计划？

**回答：**

项目里有 `search_strategy_agent.py`，它会从用户输入中提取城市、岗位方向、关键词、平台、岗位类型、薪资、经验、学历、双休和排除词。

比如用户说“上海 AI Agent，20K 以内，社招和校招都可以，不要实习，双休优先”，系统会把“上海”识别为城市，把“AI Agent”扩展成相关关键词，把“不要实习”作为硬过滤，把“20K 以内”和“双休优先”作为偏好或排序因素。

**重点句：**

我没有把所有自然语言条件都当成硬筛选，而是区分硬条件和偏好，避免把结果过滤得过少。

---

### 5.5 为什么“20K 以内”不一定硬过滤？

**回答：**

因为在招聘平台里薪资字段经常是区间，比如 15-25K、18-30K。如果直接硬过滤，很容易把一些仍然可以考虑的岗位删掉。

所以项目里会把自然语言中的“20K 以内”更多当作薪资偏好，用于排序和风险提示；只有用户在手动筛选里明确设置薪资范围时，才更接近硬筛选。这样结果不会因为条件过严而一下变得很少。

---

### 5.6 为什么“双休优先”不直接过滤？

**回答：**

“双休优先”和“只看双休”是不一样的。  
“双休优先”表示偏好，应该影响排序；“只看双休”才是硬条件。

而且很多平台不会在列表页明确写双休，如果把双休优先当成硬筛选，会误删大量其实可能合适的岗位。所以项目里默认把双休优先作为排序和风险提示，只有用户明确开启“只看公开双休/待确认工作制”时才作为硬筛选。

---

### 5.7 为什么平台选得越多，最终结果可能更少？

**回答：**

平台越多，原始候选通常会增加，但最终展示还会经过去重、岗位类型过滤、薪资、经验、学历、排除词和推荐排序。

比如同一个公司同一个岗位可能在多个平台重复出现，系统会去重；用户如果选择不要实习，实习岗位会被过滤；如果学历、经验或薪资条件过窄，也会减少最终展示数量。

所以我在搜索质量区域展示了平台抓取数、最终保留数和字段完整度，方便解释结果为什么变少。

---

### 5.8 为什么有些岗位拿不到双休、经验或地址？

**回答：**

这些字段取决于平台是否公开。有的平台列表页只给岗位名、公司和薪资，经验、福利、详细地址可能在详情页。详情页又可能需要登录或页面确认。

项目的原则是拿不到就标记未知，不编造字段。同时会在字段完整度摘要里显示哪些字段缺失，让用户知道这是平台公开信息的问题，不是系统随便漏掉。

---

### 5.9 BOSS 为什么需要特殊处理？

**回答：**

BOSS 的真实岗位数据更依赖登录状态和浏览器环境，而且登录状态可能因为会话过期或平台页面确认要求而失效。  
所以项目默认不自动打开 BOSS 登录浏览器，避免一运行就弹窗打扰用户。

只有用户手动勾选“允许打开 Boss 登录浏览器”后，系统才会打开浏览器；遇到登录或页面确认时由用户自己处理。用户完成登录后，系统复用同一个浏览器会话去抓多个关键词。

---

### 5.10 你怎么解决 BOSS 登录后又重新开页的问题？

**回答：**

之前的问题是每个扩展关键词都会单独启动一次 BOSS 浏览器，所以用户登录后，下一轮关键词又可能开新窗口，看起来像反复登录。

我把它改成批量关键词共用同一个浏览器会话。搜索开始时只创建一次浏览器，登录成功后在同一个页面里依次搜索多个关键词。同时我修正了登录态判断，区分“已登录标识”和“登录入口标识”，避免把登录按钮误判成已登录。

**可以补一句：**

这个优化不是代替用户处理平台登录，而是减少我们自己代码造成的重复开窗和误判。

---

### 5.11 上传简历后系统做了什么？

**回答：**

上传简历后，系统会先提取简历文本，再自动生成简历画像，比如技能、项目经历、教育背景、目标岗位方向等。  
为了避免重复调用模型，我用文件名和简历文本 hash 做缓存，同一份简历刷新页面后不会重复解析。

岗位匹配分两阶段：第一阶段用本地规则对全部岗位快速评分，让结果先展示出来；第二阶段默认用 DeepSeek 精排本地 Top 3 岗位，补充更细的匹配证据、缺失能力、风险点、简历动作和面试重点。

推荐结果会包含匹配理由、风险点、简历动作和面试准备重点。这样结果就不只是“有哪些岗位”，而是“哪些岗位更适合你，以及你该怎么准备”。

---

### 5.12 推荐分是怎么计算的？

**回答：**

推荐分不是单纯关键词匹配，而是综合多个因素：岗位方向、技能命中、项目关键词、薪资范围、经验要求、学历要求、双休/福利信息、字段完整度和历史反馈。

本地规则会先给全部岗位一个快速分数，保证性能和稳定性；如果有简历，DeepSeek 会对 Top 3 候选做结构化精排，模型分数会优先影响最终排序。这样既能利用大模型理解简历和 JD 的能力，也不会因为模型逐个调用而拖慢整个搜索。

DeepSeek 不可用时，系统会保留本地评分和本地解释，核心推荐流程不会中断。

---

### 5.12.1 为什么 DeepSeek 默认只精排 Top 3？

**回答：**

这是速度、成本和体验之间的取舍。一次搜索可能有几十甚至上百个岗位，如果每个岗位都调用大模型，前端会长时间没有反馈，API 成本也会增加。

所以我把匹配改成两阶段：本地规则先把全部岗位快速排一遍，然后只让 DeepSeek 精排最有希望的 Top 3。用户如果想更准，可以在高级选项里把精排数量调到 5 或 10。

**重点句：**

大模型不是越多越好，关键是把它放在最需要语义判断、且候选规模已经被收窄的位置。

---

### 5.12.2 DeepSeek 返回非法 JSON 怎么办？

**回答：**

项目里对模型输出做了结构化约束和兜底处理。Prompt 明确要求返回 JSON，并在代码里做字段归一化，比如推荐分、推荐等级、匹配证据、缺失能力、风险点等字段。

如果 DeepSeek 超时、报错或返回无法解析的结构，系统不会让页面崩掉，而是回退到本地规则评分，并在调试区保留错误信息。普通用户界面仍然能看到岗位结果。

---

### 5.12.3 Prompt 为什么要拆成文件？

**回答：**

一开始把长 Prompt 写在 Python 代码里会比较快，但后续维护很麻烦。比如简历画像、岗位匹配、JD 差距分析、面试准备包的要求都不同，如果混在业务代码里，不方便版本管理，也不方便单独调优。

所以我把它们拆到 `prompts/` 目录，每个 Prompt 都写清楚版本号、输入字段和输出结构。业务代码只负责加载和填充变量。这样代码更干净，也更像真实 AI 应用里的 Prompt 工程管理方式。

---

### 5.12.4 你简历里的量化指标怎么来的？

**回答：**

我没有把它包装成生产环境指标，因为这个项目是个人项目和本地演示系统。我的量化主要来自四个方面：

第一是**流程提效**。我把求职里原本分散的 5 个动作串成一个工作台闭环：目标解析、岗位检索、简历解析、匹配排序、面试建议。原来用户要在多个招聘网站、简历文档和大模型页面之间来回切换，现在可以在一个页面完成主流程。

第二是**模型调用降本**。岗位匹配没有对每个岗位都调用 DeepSeek，而是本地规则先覆盖全部候选岗位，再默认只精排 Top 3。所以如果一次搜索有 N 个候选，模型请求不会是 N 次，而是默认 3 次。举例来说，如果有 30 个候选岗位，全量精排要 30 次模型调用，现在默认只要 3 次，理论调用量减少约 90%。

第三是**检索和对比提效**。搜索计划会把自然语言拆成 9 类条件，包括城市、关键词、平台、岗位类型、薪资、经验、学历、双休偏好和排除词；岗位聚合会统一 10+ 标准字段，方便把不同平台的岗位放在同一张表里比较。

第四是**响应和稳定性优化**。本地规则先给全部岗位打分，页面不用等 DeepSeek 全部返回；同一份简历和同一岗位会生成缓存 key，命中后不重复请求；模型超时或 JSON 解析失败时保留本地评分，不会让页面返回空。

**重点句：**

这些指标不是“商业化效果指标”，而是我在 MVP 阶段用来证明流程提效、模型降本、响应增速和稳定性兜底的工程指标。

---

### 5.12.5 如果面试官质疑“这不算真实提效”怎么办？

**回答：**

我会承认它还不是严格 A/B 实验结果。因为项目目前是个人 MVP，没有真实用户规模和生产埋点，所以我不会说“提升转化率 XX%”或者“推荐准确率 XX%”。

但这些指标仍然有价值，因为它们能说明系统设计上确实减少了重复操作和无效调用：比如多平台从分散访问变成 1 个工作台；模型精排从全量调用变成 Top 3，以 30 个候选为例理论调用量下降约 90%；同一份简历和同一岗位通过 hash 缓存避免重复请求；岗位展示从无限长列表改成 10 条/页分页。

如果要进一步生产化，我会补埋点和评估指标，比如搜索耗时、模型调用次数、缓存命中率、用户点击岗位率、推荐采纳率和面试建议使用率，再用真实数据证明提效。

---

### 5.13 为什么未上传简历时隐藏推荐分？

**回答：**

因为没有简历画像时，推荐分只能基于岗位基础条件，不是真正针对用户个人经历的匹配。如果直接展示推荐分，用户容易误以为系统已经做了精准匹配。

所以现在未上传简历时，只展示公司和岗位信息，并提示上传简历后可以查看推荐等级和推荐分。上传后再展示个人化推荐结果。

---

### 5.14 为什么做表格和卡片两种视图？

**回答：**

表格适合快速比较公司和岗位，比如公司规模、行业、薪资、学历、经验等。  
卡片适合看单个岗位的完整信息，比如福利、招聘要求、风险提醒和建议。

结果多的时候，卡片如果一次性全部渲染会很长，所以我做了分页，默认每页 10 个，也可以切换每页数量和页码。

---

### 5.14.1 为什么不直接显示模型 JSON？

**回答：**

因为普通用户不是来调试接口的。直接显示 JSON 会让页面像开发者工具，也会让用户不知道该看哪里。

所以我把模型结果收束成中文可读信息，比如匹配证据、缺失能力、风险点、简历动作和面试重点。原始 JSON 仍然保留在默认关闭的“开发者调试信息”里，方便开发排查，但不干扰正常使用。

---

### 5.15 本地记忆保存什么？

**回答：**

本地记忆主要保存几类信息：

- 简历画像。
- 搜索历史。
- 岗位反馈。
- 投递状态。
- Agent 运行记录。
- Markdown 搜索报告路径。

它的价值是让项目不是一次性搜索工具，而是可以持续复盘。比如用户标记某些公司不合适，后续推荐就可以参考这些反馈。

---

### 5.16 DeepSeek 在项目里负责什么？

**回答：**

DeepSeek 主要负责四类语义任务：

- 简历画像解析。
- 简历和岗位 JD 的结构化精排。
- 单岗位 JD 差距分析。
- 面试准备包生成。

项目通过 OpenAI 兼容接口封装模型调用，所以后续如果要切换其它兼容模型也比较方便。同时项目不是所有逻辑都依赖大模型。像岗位筛选、字段标准化、基础推荐排序、字段完整度统计这些都有本地规则兜底，避免模型不可用时整个流程失败。

---

### 5.17 这个项目目前离生产环境还差什么？

**回答：**

我会把它定位成个人项目或原型系统，还不是完整生产系统。

如果要生产化，还需要补：

- 用户登录和权限体系。
- 更稳定的数据源接入。
- 异步任务队列和任务进度展示。
- 更完整的测试覆盖。
- 监控告警和错误追踪。
- API Key、浏览器会话和隐私数据的更严格管理。
- 更完善的部署方案和 CI/CD。

这样讲比较稳，因为既说明当前项目边界，也体现我知道后续工程化方向。

---

### 5.18 这个项目最大的难点是什么？

**回答方向 1：搜索策略**

最大的难点是把用户自然语言目标拆成合理的检索策略。  
比如“20K 以内”“双休优先”“去年毕业”“不要实习”这些条件不能全部粗暴当成硬筛选，否则结果会很少。所以我把条件分成硬过滤和排序偏好，提高结果可用性。

**回答方向 2：BOSS 登录体验**

另一个难点是 BOSS 登录浏览器的稳定性。  
BOSS 登录状态由平台控制，需要人工处理的页面应交给用户。我能做的是优化自己代码的行为，比如默认不弹窗、显式授权、单会话复用、状态软判断，减少重复登录和误关闭。

**回答方向 3：推荐解释**

推荐分如果只给一个数字，用户很难信任。  
所以我让系统同时输出匹配理由、风险点、简历动作和面试重点，让推荐结果可解释、可行动。

**回答方向 4：LLM 性能与稳定性**

如果对每个岗位都调用 DeepSeek，搜索会很慢。  
所以我做了两阶段匹配、Top 3 精排、缓存和失败兜底，让页面先有结果，再逐步补充更精准的 AI 判断。

---

### 5.19 如果让你继续优化，你会做什么？

**回答：**

我会优先优化四个方向：

1. **异步采集**  
   把多平台检索改成后台任务，前端展示进度和每个平台状态。

2. **数据质量**  
   增强详情页补全、缓存和失败重试，提高经验、福利、地址等字段完整度。

3. **推荐闭环**  
   引入更多用户反馈，让“投递、不合适、已面试”等行为影响后续推荐排序。

4. **面试工作台**  
   针对目标岗位生成题库、模拟追问、回答评分和复盘计划。

5. **详情页按需补全**  
   搜索阶段先返回列表结果，用户点开某个岗位时再补抓详情页，减少整体等待时间。

如果面试岗位偏 AI，我会重点讲推荐闭环和面试工作台；如果偏后端，我会重点讲异步任务、缓存、数据质量和监控。

## 6. 面试追问速答卡片

### 6.1 技术栈分别负责什么？

- `Streamlit`：前端工作台和交互。
- `Python`：Agent 编排、爬虫聚合、推荐排序和报告生成。

- `DrissionPage`：显式授权后的 BOSS 登录浏览器采集。
- `Markdown`：搜索报告和面试文档输出。

### 6.2 项目核心流程

用户目标 / 简历 -> 搜索计划 -> 多平台采集 -> 字段标准化 -> 去重筛选 -> 简历自动解析 -> 本地快速匹配 -> DeepSeek Top 3 精排 -> 推荐解释 -> 简历建议 -> 面试准备包 -> 报告和记忆。

### 6.3 三个核心亮点

1. 自然语言搜索计划。
2. 多平台岗位聚合与字段统一。
3. 简历画像驱动的两阶段可解释推荐。

### 6.3.1 AI 应用开发岗位最该讲的亮点

1. DeepSeek 结构化精排：让模型输出推荐分、证据、风险和建议，而不是随便生成一段话。
2. Prompt 工程化：`prompts/` 目录集中管理版本化 Prompt。
3. LLM 兜底策略：Top 3 精排、缓存、超时失败回退本地规则。
4. 产品化展示：JSON 隐藏，转成用户能看懂的中文卡片。

### 6.4 三个风险点

1. 招聘平台字段不完整。
2. BOSS 登录态可能失效。
3. 筛选条件过严会导致结果过少。
4. 大模型调用可能慢、超时或返回格式不稳定。

### 6.5 对应解决方案

1. 字段完整度统计和未知提示。
2. BOSS 登录显式授权、软判断和单会话复用。
3. 区分硬筛选和排序偏好，给出结果偏少提示。
4. 本地快速评分、DeepSeek Top 3 精排、缓存、JSON 归一化和失败兜底。

## 7. 面试官可能深挖的代码点

### 7.1 前端搜索链路

可以这样讲：

前端入口在 `app.py`。用户填写搜索关键词、城市、平台、岗位类型和高级筛选项后，点击检索会调用 `run_search`。  
`run_search` 再调用 `collect_all_jobs`，把前端条件交给聚合层。检索完成后，结果会写入 `st.session_state["current_jobs"]`，前端再根据当前视图渲染表格或卡片。

### 7.2 Agent 主编排

可以这样讲：

Agent 主流程在 `agents/career_orchestrator.py`。它先创建运行记录，然后读取简历画像和求职记忆，再调用搜索策略模块生成计划。  
接着调用聚合器采集岗位，如果有简历就做简历匹配，之后用 Ranking Agent 做推荐排序，最后生成报告并保存运行记录。

### 7.3 搜索计划解析

可以这样讲：

搜索计划逻辑在 `agents/search_strategy_agent.py`。它负责从用户目标中提取城市、关键词、岗位类型、薪资、经验、学历和排除词。  
关键点是区分硬条件和偏好，比如“不要实习”是硬过滤，“双休优先”是排序偏好，“20K 以内”更多是薪资偏好。

### 7.4 多平台聚合

可以这样讲：

多平台聚合在 `crawlers/aggregator.py`。它会根据平台列表和扩展关键词调用不同平台采集器，统一字段后做去重和统计。  
它还会记录每个平台的抓取数量、最终数量、岗位类型分布和字段完整度，方便解释为什么结果多或少。

### 7.5 BOSS 登录浏览器

可以这样讲：

BOSS 登录浏览器逻辑在 `crawlers/boss_drission.py`。  
我把它拆成创建浏览器、确认登录态、监听岗位接口、单关键词搜索和批量关键词搜索几个部分。现在同一轮搜索会复用一个浏览器会话，减少重复登录。

### 7.6 推荐排序

可以这样讲：

推荐排序在 `agents/ranking_agent.py`。  
它会综合技能命中、项目关键词、岗位方向、薪资、经验、学历、双休、字段完整度和历史反馈生成推荐分，并输出匹配理由、风险和简历动作。

如果岗位里已经有 DeepSeek 生成的 `ai_match`，Ranking Agent 会把模型给出的推荐分、推荐等级、匹配证据、缺失能力和风险点融合到最终推荐里。这样本地规则负责稳定性，模型结果负责语义判断。

### 7.7 模型调用

可以这样讲：

模型调用封装在 `llm_client.py`。  
它通过 OpenAI 兼容接口连接 DeepSeek，支持从 `config.local.yaml` 或环境变量读取 API Key。这样模型供应商和业务逻辑解耦，后续切模型时不用大改业务代码。

### 7.8 两阶段匹配

可以这样讲：

两阶段匹配主要在 `agents/resume_matcher.py`。  
`rank_jobs_for_resume` 会先对全部岗位做本地快速评分，让页面马上有排序结果；如果传入 `ai_top_n`，再对排序靠前的几个岗位调用 `deep_match_resume_to_job`。

现在默认 `ai_top_n=3`，并且会对同一份简历和同一个岗位生成缓存 key，避免重复请求 DeepSeek。模型失败时会保留本地分数，不影响结果展示。

### 7.9 Prompt 工程化

可以这样讲：

Prompt 文件集中在 `prompts/` 目录，包括：

- `resume_profile.md`：简历画像解析。
- `job_match.md`：简历和岗位 JD 精准匹配。
- `job_gap_analysis.md`：JD 差距分析。
- `interview_pack.md`：面试准备包。

`agents/prompt_loader.py` 负责加载 Prompt 并替换占位符。这样做的好处是 Prompt 可以独立版本管理，不会和业务代码混在一起。

### 7.10 前端展示收束

可以这样讲：

前端在 `app.py`。  
上传简历后会自动解析画像并缓存；有岗位时会自动先做本地匹配。普通界面展示的是简历画像摘要、推荐等级、匹配证据、缺失能力、风险点、简历动作和面试重点。

原始 JSON 不再直接展示，只放到默认关闭的“开发者调试信息”折叠区。这样产品体验更像求职工具，而不是接口调试页面。

### 7.11 自然语言求职任务

可以这样讲：

我新增了一个任务配置层，不只是让用户输入一句搜索目标，而是允许用户用自然语言描述完整求职任务，比如“上海北京深圳杭州，8 到 20K，本科，只投活跃 HR，100 字以内介绍 RAG 项目，不提薪资”。  
系统会把这段话解析成可编辑配置，包括搜索词、城市、平台、岗位类型、薪资条件、正则包含/排除、匹配阈值、打招呼字数和提示词边界。

实现上主要在 `agents/search_strategy_agent.py` 和 `memory/store.py`。解析结果不会直接执行，而是先展示在 Streamlit 表单里；用户确认后可以保存到本地 JSON，也可以按任务检索。这样做的好处是自然语言负责降低输入成本，表单负责保证可控和可修改。

### 7.12 BOSS 受控沟通

可以这样讲：

BOSS 沟通不是自动投递，也不是自动聊天。我做的是一个受控执行层：先根据岗位、简历画像、匹配结论和用户设置的提示词生成打招呼草稿；用户可以修改文本；有沟通链接时可以先干跑检查页面；最后用户确认后才发送。

代码上分两层：

- `agents/outreach_agent.py` 负责生成打招呼和回复建议，支持 20-300 字上限和用户自定义边界。
- `crawlers/boss_outreach.py` 负责复用已登录浏览器打开会话页，做页面检查和确认发送。

如果岗位不是 BOSS，或者没有沟通链接，系统只生成文本，不执行发送。每次只处理一个岗位，这样更符合我这个项目的个人 MVP 定位。

### 7.13 工作区式前端

可以这样讲：

之前所有控件都在同一个 Streamlit 页面里，简历、搜索、结果、行动建议和记忆混在一起，页面会比较乱。后来我把它拆成 4 个工作区：

- 任务配置：自然语言任务、简历上传、快速 Agent 检索、手动搜索。
- 岗位结果：搜索摘要、表格和卡片结果。
- 沟通行动：选择岗位、看匹配结论、生成 BOSS 草稿和面试材料。
- 记录记忆：Agent 解释、问答、运行记录和记忆导出。

这个改动不只是视觉调整，也让业务流程更清楚：先配置任务，再看结果，再做岗位动作，最后复盘记录。

## 10. 最推荐背下来的核心回答

### 10.1 项目核心价值

这个项目的核心价值是把求职里的“找岗位、筛岗位、判断匹配、改简历、准备面试”串成一个 Agent 工作流。它不是只抓岗位，而是结合用户目标和简历画像，输出可解释、可行动的推荐结果。

### 10.2 架构核心句

Streamlit 负责交互，Career Orchestrator 负责编排，Search Strategy 负责生成搜索计划，Crawler Aggregator 负责多平台岗位聚合，Ranking 和 Resume Matcher 负责推荐解释，SQLite 和 JSONL 负责本地存储。

### 10.3 BOSS 登录核心句

我没有让系统代替用户处理 BOSS 的登录和页面确认，而是优化自己系统的使用方式：默认不打开浏览器，用户显式授权后才启动，并且同一轮搜索复用一个浏览器会话，减少重复登录和反复开窗。

### 10.4 推荐解释核心句

推荐分不是只看关键词，而是综合技能命中、项目相关性、薪资、经验、学历、双休、字段完整度和历史反馈；上传简历后再用 DeepSeek 对 Top 3 候选做结构化精排，同时输出匹配证据、风险点和行动建议，让用户知道为什么推荐、下一步该怎么做。

### 10.5 LLM 工程化核心句

我没有让大模型接管全部流程，而是先用确定性规则完成搜索、筛选和本地评分，再把 DeepSeek 放到简历画像、Top 3 精排、JD 差距分析和面试准备包这些更需要语义判断的位置，并配合缓存、结构化输出和失败兜底保证体验。

## 11. 面试答题模板

遇到任何项目问题，可以按这个结构回答：

1. **先说业务问题**  
   为什么要做这个功能。

2. **再说技术方案**  
   用了什么技术，分了哪些层。

3. **然后说关键实现**  
   具体怎么做，比如搜索计划、字段标准化、登录复用、推荐规则。

4. **最后说结果价值**  
   提升了什么，比如效率、可解释性、稳定性、可复盘性。

示例：

> BOSS 登录优化主要解决的是用户登录后又反复弹新窗口的问题。我的方案是把原来按关键词启动浏览器，改成同一轮搜索复用一个浏览器会话。实现上，我把 Boss 采集拆成登录态判断、接口监听、单关键词搜索和批量关键词搜索几个函数，并修正登录态误判。这样减少了重复登录，也让用户体验更稳定。
